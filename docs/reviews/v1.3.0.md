## Checklist

### 1. What leaves the phone
**Fine.** The diff adds no new network call, host or payload in `lib/`.

- `LookupService` records which providers threw: `failed` holds display names
  and `why` holds the exception text.
- The app only shows `failed`, a list of names such as "iTunes", in the
  lookup sheet. `why` is read only by `live_test/`.
- `why` stays in memory and is never logged or stored by the app.

The daily live lookup check runs on GitHub's runners with fixed test titles,
so no user data is involved. PRIVACY.md and the in-app privacy page need no
change.

### 2. The user's library
**Fine.** There is no schema change, no enum change and no new deletion path.

- **Retry in `main.dart`:** if `openAppDatabase()` returns `DbFailed`, it waits
  2 s and tries once more. That function never deletes or moves the file:
  - A missing key with an existing file gives `DbKeyProblem`, which is not
    retried.
  - On a failed open the database handle is closed before returning.

  So the retry can't cause data loss.
- **Past-release fixtures:** I opened all six with SQLite. Each holds only the
  made-up library from `tool/fixtures/make_fixture_test.dart`: Heat, Arrival,
  Severance, the accented test title, Project Hail Mary, the unmatched
  podcast, the `fixture_check` setting, and random uids and watch-event uids.
  A `strings` scan found nothing else, such as paths or real titles.
  - They are unencrypted, which is fine for synthetic data.
  - The encrypted path is covered by the new update test, which uses the
    app's real key store and database.
- See L4 about which tag the update test treats as "the last release".

### 3. Untrusted input
**Fine.** No new import, paste, share or lookup parsing paths.

- The lookup sheet's new text only joins the app's own provider names.
- The device test's shared-text intent is test-only.

### 4. App lock and private items
**Fine. The lock change is an improvement.**

- **The fix:** `Overlay.wrap(child: LockScreen(...))` fixes the tooltip-less
  OK and Delete buttons. The PIN could not be submitted in 1.2.0.
  - I checked that `Overlay.wrap` exists in Flutter 3.47.9.
  - The Overlay lays its entry out to the full stack size, so the opaque
    `Material(color: surface)` still covers the whole app.
  - The app beneath stays inside `ExcludeFocus` and `ExcludeSemantics` while
    locked.
- **`unfocus()` in `initState`:** this removes a keyboard left open from the
  hidden app. A small improvement.
- **`SingleChildScrollView`:** this makes the pad reachable at large text
  sizes. It shows nothing new.
- **Tests:** regression tests were added (`test/app_lock_test.dart`). The
  device test checks:
  - FLAG_SECURE is set for "Hide in recent apps".
  - A wrong PIN does not unlock.
  - Nothing from the library is visible while locked.
- Nothing new reaches the widget, notifications or the share sheet.

### 5. Dependencies and build
**Fine, with low notes.**

- **Pins:** `jni` 1.1.2 and `jni_flutter` 1.0.4+1 are not new packages. They
  are pinned back to the versions v1.2.0 already shipped. The reason is
  documented in pubspec.yaml, SPEC §13 and PROGRESS.md.
  - I found no published advisory for either version. The only recent
    Dart/Flutter pub CVE, CVE-2026-27704, is in the pub client and is fixed in
    Flutter 3.41. The project builds with 3.47.
  - OSV and pub.dev could not be reached from the reviewer's environment.
    CI's OSV-Scanner (v2.7.0, checksum-verified) scans the resolved
    `pubspec.lock`, which includes the overrides. "Release it" refuses unless
    CI passed on the release commit, so the scan is enforced for this
    version.
  - Downside: the pin also blocks any future jni security fix. The removal
    condition is recorded, so keep an eye on it.
- **Actions:** every `uses:` in the new and changed workflows is pinned by
  commit SHA with a version comment. Every checkout uses
  `persist-credentials: false`.
- **Permissions:** the new workflows default to `contents: read`.
  `contents: write` is used only where needed: `past-release-dbs` publish and
  `promote`.
- **No risky triggers or secrets:**
  - No `pull_request_target` anywhere.
  - None of the new workflows uses repository secrets. The release build's
    `secrets: inherit` is unchanged.
  - The token in `git push` URLs is masked by Actions.
- **Untrusted inputs:**
  - `promote.yml` passes `inputs.version` through `env:` and validates it
    against `^[0-9]+\.[0-9]+\.[0-9]+$`.
  - `past-release-dbs.yml` passes `inputs.tags` through `env:`.
  - `release.yml` passes the ref name through `env:` and validates it.
- **Exception:** `demo-video.yml` interpolates `inputs.pace` straight into a
  shell script. See L1.
- **Gating:** see L3.
- **Committed files:** nothing that shouldn't be. No keystores, keys, `.env`,
  real user data or generated `*.g.dart`.
  - The GitHub handle in the walkthrough end card already appears in
    `tool/demo/make_video.py` and in the public repo URL.

### 6. Permissions
**Fine.** No AndroidManifest, Info.plist or entitlement changes in the diff.

- The device and update tests use adb settings and `install -t` only on CI
  emulators.

## Findings

| ID | Severity | File:line | Issue | Recommendation |
|---|---|---|---|---|
| L1 | low | `.github/workflows/demo-video.yml:57` | **Script injection.** `script: DEMO_PACE=${{ inputs.pace \|\| '1' }} bash …` puts a `workflow_dispatch` input directly into a shell command. The job has `contents: write`, and its later step holds `GH_TOKEN`. Only someone with write access can dispatch, so the practical risk is small. But it is the one place that breaks the repo's own "inputs go through `env:`" pattern. | Pass it through `env: DEMO_PACE: ${{ inputs.pace }}` on the step (the emulator runner inherits step env). Validate it in `record.sh`, e.g. `[[ "$DEMO_PACE" =~ ^[0-9]+(\.[0-9]+)?$ ]] \|\| DEMO_PACE=1`. |
| L2 | low | `lib/main.dart:49-56` (with `lib/data/db/open.dart:72`) | **Error logged in release builds.** The new `debugPrint('… ${result.error}')` is not stripped from release builds: it goes to Android logcat and the iOS system log. `result.error` can be a `SqliteException` from the database setup. Its `toString()` includes "Causing statement: …", so if `PRAGMA key = '<64-hex key>'` ever fails, the **database encryption key** would be written to the system log. Other errors include app-private file paths. Other apps can't read the log since Android 4.1, but adb and bug reports can. The recovery page already shows the same text on screen. That was there before, so it is out of scope, but the same fix covers it. | Log only `result.error.runtimeType`, or wrap in `if (kDebugMode)`. Better: in `_encryptedExecutor`'s `setup`, catch around `PRAGMA key` and rethrow a `StateError('could not apply database key')` without the SQL, so the key can never appear in any error text. Add a regression test that a setup failure's message contains no hex key. |
| L3 | low | `.github/workflows/promote.yml:10,44-46`, `release.yml` (`workflow_dispatch`) | **The "Release it" gate can be bypassed by anyone with write access.** (a) `workflow_dispatch` can be run from any branch, using that branch's copy of `promote.yml`, which could have the checks removed. (b) `release.yml`'s dispatch can likewise build a beta from a non-main branch, and that branch's own runs would satisfy promote. (c) Runs are matched by display `name` only, so another workflow file with `name: Device tests` would count. (d) Anyone with write access can also simply `gh release edit --prerelease=false`. The gate is therefore a procedural guard, not a technical one. It works as intended when run from main, and it fails closed: missing, cancelled or failed runs refuse. | Add `if: github.ref == 'refs/heads/main'` to the promote job. Check that the tag's commit is on main (`gh api repos/$REPO/compare/$sha...main` gives `status` `ahead` or `identical`). Filter runs by `.path` (e.g. `.github/workflows/device-tests.yml`) and `event == "push"`, not only `.name`. For a hard guarantee that the owner said yes, put promote behind a GitHub Environment with the owner as required reviewer (free for public repos), and turn on tag protection for `v*`. |
| L4 | low | `.github/workflows/upgrade-test.yml:49`, `past-release-dbs.yml:37` | **Betas count as releases.** Beta tags are plain `vX.Y.Z` (release.yml tags `v$version`), so `grep -v -- '-'` and `grep -v -- '-beta'` never exclude a beta. Once v1.3.0 is a beta, the update test for later changes runs "update from v1.3.0" even if that beta is never released. Users still on the last *promoted* release would then not be covered. It is a test-coverage gap, not a vulnerability. | Choose "last release" from GitHub releases, not tags: `gh release list --exclude-pre-releases --limit 1 --json tagName`. Alternatively, test from both the last promoted release and the latest beta. |
| N1 | none | `.github/workflows/past-release-dbs.yml:9,103` | **Any push can replace the fixture branch.** A push to *any* branch that touches `tool/fixtures/**` runs `publish` with `contents: write` and force-pushes a fresh orphan `past-release-dbs` branch. A feature branch's generator can therefore replace the fixtures the owner later copies in. `printf '%s\n' $tags` is unquoted, so the input is word-split and globbed (harmless: it is JSON-encoded by jq before use). | Limit `publish` to `github.ref == 'refs/heads/main'` or to `workflow_dispatch`. Acceptable as is for a scratch branch. |
| N2 | none | `.github/workflows/release.yml:59` | **The review gate only checks that the file exists.** An empty or "medium open" review would still pass. | Fine as a reminder gate. Optionally `grep -q '^## Fixed before release'` and refuse when the file says `medium` or `high` without a fix. |
